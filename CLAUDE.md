## Secrets (Capy)
This repo's secrets are managed by Capy.
- Run `capy help --json` for every command, its options, and its error codes.
- Always pass `--json` and branch on the `code` field, never on message text.
- To send a secret to GitHub or any other platform, run `capy deploy --json`. If no deploy target is set up, ask the human whether to set one up, and do not set one up yourself. Never push the value any other way, such as `gh secret set` or `vercel env add`. Never add `--yes` on your own.
- To add a secret, run `capy add NAME --json`. To change one, run `capy edit NAME --json`. Pipe the value in on stdin from the file or command that holds it, and never read it into your context.
- After any secret change, ask the human whether to open the keep.lock PR, and say why. `keep.lock` is the committed file that pins which version of each secret this branch uses. Until the change is merged, the repo still points at the old version, and a CI deploy that runs when `keep.lock` changes does not run. Never pass `--pr`, `--no-pr` or `--yes` before the human has answered.
- Run `capy pair --json` in an interactive terminal/PTY. After browser approval, it asks "Enable this location as [email]?" before installing the session or keys. Show the returned email to the human and obtain explicit Yes/No approval before answering. Never automatically confirm or pipe `yes`; Enter defaults to No. No upfront email is required.
- Before a command that writes, run `capy info --json` and check its `org`, `project` and `branch`. If they are not the ones the human means, stop and ask.
- If a command starts a browser sign-in, this folder belongs to an organization this machine is not signed in to. Stop and tell the human. Never complete the sign-in yourself.
- To find where a secret lives, run `capy secrets --json --name NAME`. It lists locations in the signed-in organization only, and never shows a value.
- Use `capy secrets --json --project-id <id>` when the project is known (from `capy info --json` or an earlier result). Use `--project <name>` to look a project up by name, and expect several matches: then ask the human which project, or use each match's `project_id`.
- Commands that write run bare `capy` first. If your folder and Capy differ they write nothing and exit 3 with `SECRETS_CONFLICT`, a `conflict_id`, and the differing names (fingerprints, never values).
- Show the human those names and ask, for each: pinned, local, remote or delete. Never answer for the human. Then rerun the same command with `--resolve NAME=<choice>` for every name (`NAME@TARGET=local|remote` for a platform row) and `--conflict <conflict_id>`.
- `SECRETS_CONFLICT_STALE` means Capy moved since: show the fresh rows and ask again.
- If a JSON result has an `elicitation`, write its `display` table in your reply exactly as given (never shorten or reorder it, never put it inside the question). Then ask its short `question` as an elicitation with your question tool: one question per field, using the field's own `question` followed by its `description` when it has them, and offering its `options` (or its `default`) as the choices. A field without `options` is typed in. With a `default`, offer exactly two choices, the `default` and "Cancel"; the human types any other answer in your question tool's own free-text answer. With no `default`, leave it out of the question tool: after the other questions, ask its `question` in chat and wait for the human to type the answer. On "Cancel", stop. Without a question tool, end your reply with the `question` and wait for the human to answer in chat. Then run the elicitation's answer command with what the human chose. Never answer it yourself and never add `--yes` on your own.
- Only when the human asks to create a project, run `capy project create --json`, adding the name, `--branch <branch>` and `--protected yes|no` only if the human already gave them. It creates nothing until it has all three and returns an `elicitation` asking for the rest: that is how you ask the human, so do not ask your own question first.
- Only when the human asks to delete a project, run `capy project delete <name> --json` with the name they gave and without `--yes`, even if this folder's project is deleted or is a different one: it looks the name up in the organization, not in this folder. It changes nothing and returns an `elicitation`: that is how you ask the human, so do not ask your own question first. Only an org owner or admin can delete or restore a project.
- `PROJECT_DELETED`, or `project.state` `"deleted"` in `capy info --json`, means an org owner or admin deleted this folder's project. Stop and tell the human. An org owner or admin can restore it with `capy project restore <project_id>` (the id is in `keep.lock`). Never create a new project and never edit `keep.lock`. This is about this folder only: it never stops a delete or restore the human asked for by name.
- Only when the human asks to rename a project, run `capy projects rename <new-name> --json` in the project's folder, or add `--project-id <id>` to run it anywhere. Only an org owner or admin can rename a project.
- Only when the human asks to delete a Capy branch, run `capy branch -D <name> --json` without `--yes`. It deletes nothing and refuses with `CONFIRMATION_REQUIRED`: ask the human, and add `--yes` only on their yes.
- In a folder that has `keep.lock` and no `.env` (a fresh clone or worktree), run `capy checkout <branch> --json` with the branch the human names. It writes that branch's `.env`.
- `capy users`, `capy projects`, `capy secrets` and `capy invite` need no project folder. `ORG_SELECTION_REQUIRED` means the account is in several organizations and the folder names none: show the human the `orgs` it lists and stop.
- Never print, log, or commit secret values.
- To set a value, pipe it from the command that produces it: `<cmd> | capy edit NAME --json`. Never put a value in a command argument, an `echo`, or a heredoc — it would land in your context and the shell history.
